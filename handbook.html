Week 1

Bytes must reach compute

Most modern inference tricks are data-movement tricks. The question is not only how many operations you perform, but where the operands live and how often you move them.

Typical server with a discrete PCIe GPU

The CPU and host RAM are separate components. The GPU is also a separate processor with its own memory. PCIe connects the host side to the GPU side.

Interconnect is a general word for the communication path between components. It includes the physical wires or package links, the controllers at each end, and the protocol used to move commands and data. In this diagram the CPU-to-GPU interconnect is PCI Express. DDR channels are a different interconnect between the CPU's memory controller and host RAM. HBM/GDDR wiring is another, much wider local interconnect between the GPU and its device memory.

1. CPU package

The CPU contains execution cores, registers, caches, a memory controller, and usually the PCIe root complex. It runs Python, tokenization, the request scheduler, and CUDA runtime calls. It is not the same thing as RAM.

2. Host RAM

Host RAM is the computer's DDR memory. It stores the Python process, tokenizer data, model files while loading, and CPU tensors. CPU cores reach it through the memory controller and DDR channels.

3. PCIe interconnect

PCIe is a packet-based I/O link. The CPU submits commands to the GPU and data transfers cross its lanes. PCIe bandwidth is far below local GPU-memory bandwidth, so repeatedly moving weights or KV state over PCIe can dominate inference time.

4. GPU processor

The GPU contains streaming multiprocessors, registers, on-chip shared memory/L1, L2 cache, copy engines, and compute pipelines. Kernels execute here, not in HBM.

5. GPU memory

HBM or GDDR stores model weights, KV cache, activations, and workspaces. It is physically separate from host RAM. The GPU reaches it through its own memory controllers and a very wide local bus.

6. DMA / copy engine

The CPU normally schedules a transfer; it does not copy every byte itself. A DMA-capable GPU copy engine pulls from pinned host RAM across PCIe and writes into GPU memory. Dependencies and CUDA streams decide when compute may use the result.

Terminology warning: NVLink is usually a high-bandwidth GPU-to-GPU fabric. NVLink-C2C is a coherent chip-to-chip link used in tightly integrated systems such as Grace Hopper. Neither should be drawn as the default CPU-to-discrete-GPU path; ordinary servers usually use PCIe.
Your M2 Pro is different: CPU and GPU share one physical DRAM pool through Apple's system-on-chip fabric. There is no PCIe hop into separate VRAM, but CPU/GPU caches, logical buffers, synchronization, copies/blits, and shared-memory bandwidth limits still matter.

Compute-bound

Math pipelines are the limiting resource. Lower precision, faster kernels, or fewer FLOPs may help.

Bandwidth-bound

Execution waits for bytes. Quantization, reuse, fusion, and smaller KV state may help.

Launch-bound

The GPU is starved by CPU/driver overhead and tiny kernels. Batching, compilation, graphs, and fusion may help.

Scheduler-bound

Queueing and interference dominate. Admission, prioritization, chunking, or capacity may help.

Roofline calculator

Count multiply + add as two FLOPs. Match peak compute to the operation dtype and name the memory level. Real kernels also pay launch, synchronization, occupancy, and access-pattern costs.

Weeks 2-3

KV cache, from formula to product constraint

For uniform layers, logical KV payload is \(2BLSH_{kv}d_hb\). The factor two is K and V. Runtime memory is larger because allocation and metadata are not free.

KV memory calculator

Does not include block tail waste, scales, alignment, temporary workspace, or parallelism replication.

MHA

One K/V head per query head. Highest KV capacity and bandwidth.

GQA

Groups of query heads share K/V. KV ratio to MHA is roughly Hkv / Hq.

MQA

One K/V head shared by all query heads. Smallest KV, but it is a model architecture choice.

Week 4

Kernels are controlled memory traffic

Principle

FlashAttention

Tiles exact attention through SRAM and uses online softmax. It avoids quadratic score storage, not quadratic dense-prefill arithmetic.

Technique

Fusion

Removes intermediate HBM round trips and launches. Too much fusion can increase registers and spills.

Technique

Quantization

Shrinks weights or KV. Speedup requires supported kernels and a quality gate.

Runtime

CUDA graphs

Reduce host launch overhead for repeated shapes. They do not inherently reduce model FLOPs or tensor HBM traffic.

Algorithm

Speculation

Trade draft work for fewer serial target calls. Value depends on acceptance and batch saturation.

Common error: “The GPU is only 40% utilized” is not a diagnosis. Utilization can mean any kernel was active during a sample, not that tensor cores or memory bandwidth were saturated.
Week 5

The scheduler sells the SLO

The same model and kernel can deliver very different user experience depending on queueing, batching, prefill interference, cache locality, and admission.

Continuous batching

Schedule every iteration. Completed requests leave and new requests enter. This removes request-level padding, not autoregressive dependency.

Chunked prefill

Break long prompts into pieces so they do not block decode. Smaller chunks protect ITL but can hurt TTFT and efficiency.

Admission

Output length is unknown. Reserve too much and waste memory; reserve too little and preempt, swap, or reject.

Disaggregation

Separate prefill and decode pools. Gain isolation; pay duplicate weights, KV transfer, routing, and operational complexity.

Founder metric: optimize SLO-good requests per accelerator-hour, not unconstrained tokens per second.
